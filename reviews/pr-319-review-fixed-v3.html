What went wrong in v2, in plain terms. v2's F-007 fix and v1's F-006 fix were each reasonable in isolation, but they interacted badly: F-006 made user_role_master (the wizard's role checkboxes) mirror almost every real Spatie role, and F-007 then wired those checkboxes straight into syncRoles() with no authorization check and a "preserve what isn't offered" rule that assumed the offered set would stay small. Once the offered set became ~20 of 22 roles, that assumption broke: any authenticated user could grant themselves almost any role (F-018), and saving any member's record could silently strip roles assigned via the separate Users screen (F-019). Both were caught by the user's own follow-up review, not by the verification in v2 — that verification used a synthetic "totally unrelated" role that happened to sidestep exactly the scenario that mattered. Fixed properly below, and re-verified against the exact scenarios the review reproduced.

FIXED v3 F-018 — authorization gate on the RBAC-granting code path

Root causemember/store, member/update, admin/setup/member/store, admin/setup/member/update/{id} all carry only web, auth middleware (confirmed via php artisan route:list), and every StoreMemberStep*Request::authorize() returns true. v2's syncSpatieRolesFromWizardSelection() had no check of its own, so any authenticated member could edit their own record, tick "Super Admin", and grant it to themselves.
FixNew MemberController::actingUserCanManageRbacRoles(): hasRole('Super Admin') || hasRole('Admin') || hasRole('SuperAdmin') || hasRole('Super-Admin') — the acting user (Auth::user()), not the member being edited. This is the same hasRole() helper and the same admin-role-name convention already used to gate privileged actions throughout this codebase (e.g. CalendarController, CourseController, DuplicateIDCardRequestController) — there is no permission:/role: middleware or policy layer anywhere in this app to hook into instead, including on the existing, already-shipped users.assignRoleSave route this code mirrors. syncSpatieRolesFromWizardSelection() now returns immediately, before touching Spatie at all, if this check fails.
What did not changeA non-admin's Member wizard submission still writes employee_master, user_credentials, and employee_role_mapping exactly as before — only the newer Spatie-RBAC side effect is skipped for non-admins. The wizard's core create/edit functionality is identical for every user regardless of this check.
VerificationAgainst an isolated clone database (sargam_pr319_v3_test2, dropped after) with real production-representative role data: a non-admin actor invoking the method against a target member with "Doctor" selected left the target's roles completely unchanged; the same call as an admin actor granted it. Committed as an executable regression test — see F-022.
Filesapp/Http/Controllers/Admin/MemberController.php — new actingUserCanManageRbacRoles() method, called at the top of syncSpatieRolesFromWizardSelection().

FIXED v3 F-019 — role sync no longer keyed off the (now nearly-universal) offered set

Root causev2 computed "roles to preserve" as the complement of "user_role_master options that match a real Spatie role." Before F-006, that offered set was small, so the complement (everything preserved) was almost everything. After F-006's sync migration, the offered set covers ~20 of 22 roles, so the complement collapsed to almost nothing — saving a member with only "Doctor" ticked would syncRoles(['Doctor']) and silently strip any other role, including ones granted via Role & Permission > Users.
FixReplaced "preserve = complement of offered" with "revoke only what this same wizard granted last time." employee_role_mapping is already the durable, wizard-only record of what this screen has ever selected for a member — nothing else writes to it. update() now captures that table's existing rows for the offered roles before deleting them ($previouslySelectedRoleIds), and passes that alongside the newly-submitted selection into syncSpatieRolesFromWizardSelection(). The method now only ever removes a Spatie role that was in the previous wizard-selection set and isn't in the new one; a role granted any other way is never touched, no matter how large the offered set is. store() has no "previous" selection (new member), so it only ever adds, never removes.
VerificationReproduced the review's exact scenario against the isolated clone: gave a target member "FC-Sec-Audit" directly (simulating the Users screen), then had an admin actor save the wizard with only "Doctor" ticked → result Doctor, FC-Sec-Audit (both present, nothing stripped). Then had the admin save again with Doctor unchecked (passing the previous selection) → result FC-Sec-Audit only (Doctor correctly revoked, FC-Sec-Audit still untouched). Both reproduced as executable tests — see F-022.
Filesapp/Http/Controllers/Admin/MemberController.php — syncSpatieRolesFromWizardSelection() signature and logic rewritten; update()'s role-mapping block captures $previouslySelectedRoleIds before its existing delete call.

FIXED v3 F-020 — role-sync migration's down() no longer guesses by name

Root causedown() identified "rows this migration could have added" by re-running a name+usage test (exact match against a current role name, not currently referenced in employee_role_mapping) — the same test used to decide insertion, not a record of what was actually inserted. A pre-existing row with that exact name (e.g. "HAC Person", pk 135, which up() explicitly skipped because it already existed) passes that same test and was deleted anyway. The round-2 review proved this by running migrate then migrate:rollback on a clone and watching user_role_master go 19→35→18 rows, not back to 19.
Fixup() now inserts each new row individually with insertGetId() (rather than one bulk insert()) and records the exact pk of every row it creates in a small tracking table, pr319_role_sync_log, created on first use. down() deletes only the pks recorded there — never a row it can't prove it created, regardless of name — and drops the tracking table afterward. The pre-existing "still in use" safety check is kept as an additional guard on top.
VerificationAgainst an isolated clone (sargam_pr319_v3_test, dropped after) seeded from real data: added one throwaway role with no user_role_master match, ran up() (30→31 rows, one row logged), confirmed "HAC Person" (pk 168 in the clone) was present and untouched, ran down() (31→30, log table dropped), and confirmed "HAC Person" was still present — the exact case that failed before. Also verified: re-running up() after down() is idempotent, and a row up() inserted that later became "in use" via employee_role_mapping survives down(), per the existing safety check.
Filesdatabase/migrations/2026_09_10_000001_sync_user_role_master_with_roles.php — rewritten up()/down().

FIXED v3 F-023 — step 6 dropdown options no longer loaded on every step

Root causeF-001's original exit criteria wanted step6DropdownOptions() (two queries: SalaryGrade::all(), EmployeeCategoryMaster::pluck()) loaded only when rendering step 6. v1 fixed the missing-schema half of F-001 but left the call unconditional in both loadStep($step) and editStep($step, $id), so every one of the 6 wizard steps ran both queries regardless of which step was actually being shown.
FixBoth methods now only call step6DropdownOptions() when (int) $step === 6; every other step gets [[], []] for those two variables instead.
VerificationConfirmed via grep that gradePayOptions/employeeCategoryOptions are referenced only by steps/step6.blade.php and edit_steps/step6.blade.php — no other step view uses them, so passing empty arrays for steps 1–5 is behaviorally identical to before from those views' perspective.

FIXED v3 F-024 — orphaned uploads cleaned up on transaction failure

Root causestore()/update() write the uploaded profile picture / additional document to the public disk before DB::transaction() opens (necessary, since the file has to exist before its path can be saved to employee_master). If the transaction then fails and rolls back, the already-written file is never cleaned up.
FixWrapped each DB::transaction() call in a try/catch. On any \Throwable, a new deleteUploadedMemberFiles() helper removes exactly the file(s) uploaded in that specific request (only ever non-null when hasFile() was true for this submission — an unrelated pre-existing file path is never touched), then the exception is rethrown so the existing error response behavior is unchanged.
Filesapp/Http/Controllers/Admin/MemberController.php — store(), update(), new deleteUploadedMemberFiles().

FIXED v3 F-006 — near-duplicates investigated: not duplicates, left alone deliberately

What the review flagged"Student-OT" beside "Officer Trainee", and "Internal Faculty"/"Guest Faculty" beside "Faculty", looked like semantic near-duplicates this migration should collapse, and user_role_master's growth from 19 to 35 rows looked like uncontrolled list growth.
InvestigationChecked how each name is actually consumed elsewhere in the codebase before concluding whether they're duplicates:
  • Student-OT: grepped for every assignRole('Student-OT')/syncRoles(...) call — none exist. It is never assigned as a Spatie role at all; it's injected into the session only, at login (LoginController.php, Authenticate middleware), exactly as the hasRole() helper's own docblock says. It has no relationship to the real Spatie "Officer Trainee" role beyond superficially resembling it.
  • Internal Faculty / Guest Faculty: checked via hasRole() 17 and 16 times respectively across AttendanceController/CalendarController/etc. — including methods that branch on them separately from a plain hasRole('Faculty') check in the same method (e.g. CalendarController.php lines 2490, 2536, 2565). They are relied on throughout as distinct categories, not aliases of "Faculty".
Merging any of these would silently change existing, working authorization behavior elsewhere in the app — the opposite of "major functionality should not change." The row-count growth is real but is 16 legitimate real-Spatie-role rows the sync migration correctly added (F-001/F-006 original scope), not duplication.
FixNo data change. Documented this reasoning directly in the migration's docblock so a future reader doesn't re-flag the same names without re-doing this check, and so nothing later "cleans up" what only looks like duplication.
