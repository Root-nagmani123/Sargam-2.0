Blocker & High — the schema gap (F-001, F-002, F-003, F-004)

FIXED F-001 / F-002 / F-003 — missing Step 6 schema

Root cause foundOn this machine's database, employee_category_master and payroll_salary_master.employee_category_master_pk/basic_pay already exist — but as legacy tables/columns, never created by any tracked migration. employee_category_master holds real historical data back to 2013. That's exactly the gap the review found on its own test database: a fresh or CI environment has no migration to create any of this, so the app 500s on every wizard step and the basic_pay migration's after() anchor fails.
FixTwo new migrations, ordered to run before the existing basic_pay migration:
  • 2026_08_18_235800_create_employee_category_master_table.php — creates the table (exact structure matched from this database's SHOW CREATE TABLE) only if it doesn't already exist.
  • 2026_08_18_235900_add_employee_category_master_pk_to_payroll_salary_master.php — adds the column, anchored after salary_grade_pk (a column that genuinely exists), only if it doesn't already exist.
Both are guarded with Schema::hasTable() / Schema::hasColumn(), so on any environment where this legacy schema already exists (including this one, and presumably production) they are pure no-ops that touch zero rows. Their down() methods are deliberately no-ops too — a migration can't tell “I created this, safe to drop” from “this already held real data”, so the safe choice is never to drop it.

The original 2026_08_19_000001_add_basic_pay_to_payroll_salary_master.php migration was not modified — once its anchor column exists (created by the migration above it), its existing after('employee_category_master_pk') works exactly as originally written.
VerificationRan all three migrations via php artisan migrate --path=... (bypassing an unrelated, pre-existing broken migration elsewhere in the queue — a MySQL-version collation issue, not touched here). Confirmed via information_schema: employee_category_master row count unchanged (22, before and after — correctly a no-op), payroll_salary_master.employee_category_master_pk unchanged. On a genuinely fresh database these same migrations would instead create both from scratch.

FIXED F-004 — max(pk) + 1 race condition

FixNew migration 2026_09_18_000001_add_auto_increment_to_payroll_salary_master_pk.php runs ALTER TABLE payroll_salary_master MODIFY pk BIGINT(20) UNSIGNED NOT NULL AUTO_INCREMENT, guarded by an information_schema check so it's a no-op if already applied. PayrollSalaryMaster's $incrementing flipped from false to true (with 'pk' removed from $fillable, since nothing sets it anymore), and MemberController::saveStep6PayrollData() no longer computes max('pk') + 1 — Eloquent lets the database assign it.
VerificationConfirmed 897 pre-existing rows and their pk values (range 1001595058–1999894061) were completely untouched by the ALTER. Confirmed via information_schema that the table's auto-increment counter was automatically set to 1999894062 (max + 1). Created a real row through the model afterward and confirmed it received pk 1999894062 with no manual assignment, then deleted that test row. AUTO_INCREMENT is a database-native guarantee against the exact race the review described (two concurrent SELECT MAX / INSERT sequences colliding) — it isn't something a concurrency test needed to reproduce here, since it removes the class of bug structurally.

Medium

FIXED F-005 — no transaction across the five writes

Fixstore() and update() in MemberController.php now wrap the employee_master / payroll_salary_master / user_credentials / role-mapping writes in DB::transaction(function () use (...) { ... }). File uploads (which happen before the transaction, as they always did) are unaffected — only the DB writes are atomic now.
VerificationConfirmed via php -l and a full re-read of both methods that the closures capture exactly the variables they use and return correctly. An exception thrown anywhere inside either closure (e.g. the F-003 failure mode, now closed, or any future one) rolls back every write in that transaction automatically — no orphaned employee_master row without credentials/roles.

FIXED F-006 — role-sync migration created near-duplicates

Fix2026_09_10_000001_sync_user_role_master_with_roles.php's matching now normalizes names (lowercase, trim, collapse runs of space/hyphen/underscore to one space) before comparing, so “Super Admin” and “Super-Admin” are recognised as the same role and no second option is inserted. down() is no longer a bare no-op: it now removes rows that exactly match a still-existing roles.name and aren't currently assigned to any member, leaving anything in use (or no longer matching) untouched.
VerificationDirectly exercised the migration's own normalize() method: confirmed "Super Admin" and "Super-Admin" now produce the identical key. Simulated the exact near-duplicate scenario end to end: inserted a test role "Test-Role-XYZ" into roles alongside an existing "Test Role XYZ" (space-separated) in user_role_master, ran the migration's up(), and confirmed no second row was inserted. Then verified down(): an exact-match, unused test row was removed, while the near-duplicate (space-separated) survivor was correctly left alone since it isn't an exact match. All test rows cleaned up afterward.

OPEN — human decision F-007 — wizard role selection never reaches Spatie RBAC

Why this wasn't changedThe review itself frames this as requiring a written product/engineering decision before any code changes: either wire the Member wizard's role checkboxes into syncRoles() so the list means what it visually appears to mean, or keep user_role_master visibly distinct from roles so it's never mistaken for granting RBAC access. Both are legitimate, materially different directions, and choosing between them isn't a bug fix — it's a scope decision the review explicitly routes to the Engineering lead. Acting on this unsupervised risks silently changing what “assigning a role” means for every admin who uses this screen.
StatusLeft exactly as found. Needs: written decision from Engineering lead, per the original review's Human Actions Required list.

FIXED F-008 — deactivating a role silently stripped it on next edit-save

Fixupdate()'s role-mapping replacement no longer deletes every existing mapping before recreating from the submitted checkboxes. It now computes UserRoleMaster::getUserRoleList()->keys() (the same active-only set the checkboxes are rendered from) and only deletes-and-replaces mappings whose role is in that set. A mapping pointing at a role that's since been deactivated — which the form has no checkbox for and therefore can't post back — is left untouched.
VerificationPicked a real, currently-active role (pk 123, “Training-Induction”), confirmed it appears in getUserRoleList()'s keys, deactivated it, and confirmed it immediately drops out of that key set — which is exactly the condition the new whereIn($offeredRoleIds) delete relies on to skip it. Restored the role to active afterward, confirmed via a fresh query.

PARTIALLY FIXED F-009 — basic pay integer with no lower bound

Fix appliedStoreMemberStep6Request::rules(): 'basicpay' => ['nullable','integer','min:0'], with a matching validation message. This is exactly what the review said to do “regardless” of the precision decision.
Left openWhether basic_pay should be decimal(15,2) instead of integer (to match every sibling money column on the same table). The review is explicit that this is a domain question a review session can't answer from code — whether this organisation's basic pay is ever fractional. Changing the column type without that confirmation risks either silently truncating real paise values or being unnecessary schema churn.
Verificationphp -l passed; rule change is a single additive constraint with no other code path depending on the previous absence of a lower bound.

FIXED F-010 — a step-6 value could never be cleared

FixmapStep6Data() rewritten. It still returns [] (and therefore still skips writing anything) when the admin leaves the entire step untouched — preserving the original “don't create an empty payroll row for a member who never uses this step” behaviour. But once at least one of the five fields has a value, all five keys are now returned together, with any field submitted as an empty string mapped to null instead of being dropped — so a field the admin deliberately blanks is actually cleared on save.
VerificationInvoked mapStep6Data() directly via reflection with two requests: an entirely empty one (confirmed result [], matching the original “skip” behaviour) and one with basicpay filled and bankname submitted as an empty string (confirmed the result carries all five keys, with bank_name => null and basic_pay preserved) — exactly the fix the review asked for, without changing the untouched-step behaviour.

FIXED F-011 — no cache invalidation from Department/Designation saves

FixIdentified the controllers actually wired to the Department Master and Designation Master screens (DepartmentMasterSetupController, DesignationMasterSetupController — confirmed via the route file, since a second, unrouted “Master” controller pair also exists for each and was not touched). Their store(), update() and delete() methods now call MemberDataTable::bumpListingCacheEpoch() after the write, matching the same pattern MemberController already uses.
Verificationphp -l passed on both files. The epoch-bump call is the exact same static method the Member listing's own create/update/delete paths already call, so its effect (forcing a fresh /member listing fetch on the next request) is already proven correct by the existing code it's copied from.

FIXED F-012 — unescaped department/designation names (CWE-79)

FixMemberDataTable.php's department and designation column closures now wrap the interpolated name in e() before placing it inside the raw <label> HTML. The columns remain in rawColumns() (needed for the surrounding <label> tag to render as markup), but the value itself is now escaped.
Scope noteThe pre-existing employee_name column has the identical unescaped pattern (interpolating first_name/middle_name/last_name) but was not part of this PR's diff and is not one of the 17 findings — left untouched, consistent with the “don't change functionality beyond what's asked” constraint for this fix pass.
Verificationphp -l passed. e() is Laravel's standard HTML-entity escaping helper; wrapping just the interpolated value (not the surrounding tag) is the same pattern the review's required change described.
