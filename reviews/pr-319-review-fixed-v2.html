FIXED v2 F-007 — wizard role selection now reaches Spatie RBAC

DecisionWire the Member wizard's Role Assignment checkboxes to Spatie syncRoles(), the same mechanism UserController::assignRoleSave() already uses for the dedicated Role & Permission > Users screen — so ticking a role here now actually grants it, matching what admins already assume it does.
The risk this had to avoiduser_role_master (this screen's checkbox source) is a mix of 21 rows that exactly match a real Spatie role and 9 that don't (“Internal Faculty”, “Staff”, etc. — plain HR tags, no permission meaning). A naive $user->syncRoles($selected) using only what's checked on this screen would wipe every Spatie role the member has that isn't offered here at all — including anything assigned through the separate Role & Permission > Users screen, the moment anyone saves this wizard for any reason.
FixNew private method MemberController::syncSpatieRolesFromWizardSelection():
  1. Resolves which user_role_master options offered on this screen correspond to a real roles row by name ($spatieRoleNamesOffered).
  2. Of what the admin actually checked, keeps only the ones in that set ($selectedSpatieRoleNames) — a checked “Internal Faculty” box has no Spatie effect, same as before.
  3. Reads the member's current Spatie roles and keeps only the ones not in $spatieRoleNamesOffered — i.e. whatever this screen has no checkbox for at all.
  4. Calls syncRoles() with the union of those two sets, then clears Spatie's permission cache (matching UserController's existing pattern).
Net effect: this screen fully controls exactly the roles it shows a checkbox for (check it → granted, uncheck it → revoked) and never touches anything assigned elsewhere. Called from inside the same DB::transaction() already added in v1, right after the existing EmployeeRoleMapping write, in both store() and update().
VerificationBuilt entirely from throwaway data, deleted afterward — no real employee's roles were touched during testing:
  1. Created a fake Spatie role Test-Unrelated-Role-XYZ and a fake user_credentials row; assigned that role directly (simulating “set via the other Users screen”).
  2. Called the new method as if the admin checked “Doctor”: result was Doctor, Test-Unrelated-Role-XYZ — Doctor granted, unrelated role preserved.
  3. Called it again with nothing checked (simulating unchecking Doctor): result was Test-Unrelated-Role-XYZ — Doctor correctly revoked, unrelated role still preserved.
  4. Deleted the fake user and fake role; confirmed both gone and zero leftover model_has_roles rows.
Filesapp/Http/Controllers/Admin/MemberController.php — new method + two call sites; new imports for User, UserRoleMaster (destructured), Spatie\Permission\Models\Role.
