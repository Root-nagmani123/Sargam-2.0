How this was produced — reproduce it yourself

  1. Walked every .blade.php under resources/views; kept the 292 that contain a <table> plus a @foreach/@forelse/$dataTable.
  2. Ran php artisan route:list --json, resolved each GET route’s controller method, and extracted its view(...) calls — leaving 187 views that a user can actually navigate to. Partials, PDFs and print templates dropped out here.
  3. Credited all four chrome sources before flagging anything: the global enhancer public/js/datatable-global-ui.js, the table.datatable auto-init in admin/layouts/footer.blade.php, the shared components/mess-master-datatables.blade.php, and the two JS-side inits in public/admin_assets/js/custom.js (attendanceTable, group-mapping-table).
  4. Opened each survivor and confirmed the gap by hand — the numbers below are file + line references, not regex guesses.

  5. One unguarded ->timetable among three optional() siblings 500’d the send-notice page. Fixed.
  6. Course List’s Status Filter is a hard 500 — confirm_status lives on another table. Guarded and hidden; needs a schema decision.

Found while fixing — a separate live 500 on /registration/forms/{form}/courselist

The page’s Status Filter queries fc_registration_master.confirm_status. That column does not exist on that table — it belongs to form_submissions (migration 2025_04_17_093502). Every use of the filter returns Unknown column 'confirm_status' in 'where clause', and has since it shipped; ?statusval=1 has never rendered a page. The same bug is in the export path.

Not remapped, because it can’t be done safely: fc_registration_master.status holds '1' or NULL, which does not carry the confirm / not-confirm meaning the dropdown offers — pointing at it would silently show the wrong rows. Both call sites are now guarded with Schema::hasColumn and the view hides the control while the column is missing, so the page can no longer crash and the filter reappears by itself the day the column lands. Deciding what “confirmed” means here is a product call.

Found while adding search — a filter that could be defeated, and a slow query

Searching defeated the status filter on /security/employee-idcard-approval/all. Its permanent-requests branch read whereHas('employee', …)->orWhere('id_card_no', …) with the orWhere outside the group, so the SQL became … AND EXISTS(name) OR id_card_no LIKE ? AND id_status = ? — and because AND binds tighter than OR, any row matching on card number escaped every other constraint. Measured: with the status filter allowing 1 row, the old shape returned 4. Both alternatives are now wrapped in one closure, which is how the contractual branch beside it was always written.

/security/visitor-pass is a 192,974-row grid. Reaching the Visitor(s) and Host Employee columns with two whereHas() subqueries OR-ed alongside the LIKEs cost 2.91s at query level (6.8s for the page) because it defeats the index. Resolving those two relations to id lists first and using whereIn returns the identical 4,876 rows in 0.38s — page render 6.8s → 1.4s.

Partial chrome — two judgement calls, and why

/registration/forms got a count, not a pager. It is a collapsible parent → child tree; slicing a flattened tree by row would strip children away from the parent that owns them. Measured first: 32 top-level forms, 71 rows in total — nothing to page. The honest gap was the missing count, which now also tracks the client-side filter, because a static count beside a filtered table is worse than none.

/admin/mess/reports/purchase-sale-quantity got a count, not a search box. Its Item filter is already a searchable Choices multi-select, alongside Category and Store — a free text box would duplicate it. The footer rendered page links and never a total; it now shows “Showing N of M items”, using vendor.pagination.custom rather than pagination::bootstrap-5, because the Bootstrap view prints its own “Showing 1 to 10 of N results” and the count appeared twice on the first attempt.

Found while adding search — two more live defects, now fixed

Caste Category was querying a column that does not exist. The whole page is written against caste_category_master.category_name; the real columns are Seat_name / Seat_name_hindi. The Name cell therefore rendered blank on every row, and a search over that column 500s. The grid’s read path now uses Seat_name and the names display. The write path is still broken — store() and update() validate with Rule::unique('caste_category_master','category_name') and assign $model->category_name, so Add/Edit cannot work. Left alone: choosing whether to rename the column or the code is a schema decision.

A missing ) killed the inline script on four setup pages. escapeHtml() in caste-category, department, designation and employee-group read .replace(/…/g, c => ({…}[c]); } — one closing paren short, which is a parse error, which means the entire script block never ran and the Add/Edit modals were dead. Fixed, and the map now covers ' as well (the regex matched it but the lookup returned undefined, so an apostrophe would have been written into the row as the string “undefined”).

Left undone on purpose — /fc/status/data

The 18th grid in this group. Unlike the other seventeen it is not the shared master template: it is a tabbed, AJAX-refreshed fragment whose rows come from FcRegistrationStatusService::participantsForTab(). Adding search means a new service parameter plus threading the term through the tab-switching and paging JS that rewrites the URL — a different change from the one-line filter the other grids needed, and on a public-facing page.

Faculty Average search — done, and kept consistent with its exports

This was deferred once because the report is reached through two route families (feedback.average.* for admins, faculty.session_feedback.average.* for faculty) and offers Excel, PDF and Print — six paths that could disagree with the screen. On a closer look the faculty routes are thin delegates to the same three FeedbackController methods, so it is three query sites, not six.

All four sites — screen plus the three exports — now call one shared applyFacultyAverageTopicFilter(), so the filter cannot drift between what you see and what you download. Verified rather than assumed: for the same term the screen reports 1 of 95 and the Print view renders exactly 1 data row, while the Excel and PDF payloads shrink. A search wired only into the screen would have been a worse bug than the missing box.

Before you fix any of this — one latent trap

The global enhancer sets dom app-wide to a d-none row (applyGlobalDefaults, datatable-global-ui.js:441–450), but it skips relocating the controls when a table carries dt-legacy-layout or data-sargam-dt-ui="false". Convert one of the pages above to a DataTable and opt it out, and all three controls vanish silently — it looks like a CSS bug and isn’t.

Every current opt-out — fcregistrationmaster_list, import_students, enrollement, student_courselist, faculty_table — supplies its own explicit dom, so nothing is broken by this today. Keep that invariant.

Confirmed healthy — don’t re-audit these

/subject, /subject-module, /memo/discipline, /admin/memo-notice-management, /enrollment/create and /my-course-participant all disable the DataTables chrome but ship a complete hand-rolled replacement (search box + Showing line + Laravel paginator).

The whole Mess master module (client-types, itemcategories, itemsubcategories, stores, storeallocations, my-bills) looked bare on a first pass but pulls full server-side chrome from the shared components/mess-master-datatables include. Likewise /attendance, whose DataTable is built in custom.js:1967, not in the Blade file.
